10.2 Why automatic OAuth could not work
- GitHub's protected-resource metadata points to the issuer
  https://github.com/login/oauth.
- The RFC 8414 metadata at
  https://github.com/.well-known/oauth-authorization-server/login/oauth lists
  the authorization, token and device endpoints but no registration_endpoint.
- OpenCode's MCP OAuth client requires dynamic client registration, so
  `opencode-v2 mcp auth github` reports "not an OAuth-capable remote server"
  and the earlier attempt failed with "does not support dynamic client
  registration". This is a limitation on GitHub's side, not a config error.

10.3 What was done
1. Installed GitHub CLI 2.105.0 with winget (package GitHub.cli).
2. Ran `gh auth login --web` with scopes repo, read:org, read:user, gist,
   workflow. The one-time device code 6959-F598 was approved in the browser.
   Result: logged in as vijayaragavan-dev; token stored in the Windows keyring.
3. Moved the token into the user environment as
   GITHUB_PERSONAL_ACCESS_TOKEN without printing it, and persisted it with
   `opencode-v2 service set env GITHUB_PERSONAL_ACCESS_TOKEN`.
4. Set the github entry to "disabled": false. The header remains
   "Authorization: Bearer {env:GITHUB_PERSONAL_ACCESS_TOKEN}"; no token was
   written to opencode.jsonc.
5. Restarted the background service. `mcp list` reports github connected and
   a live get_me call succeeds.

10.4 Root cause of the first failure
The background service had been started before the variable existed. Windows
process environments are fixed at creation, so the header resolved to
"Bearer " and the endpoint returned 400 "Authorization header is badly
formatted". A user-level setx alone is not enough for a running service; the
service must be restarted with the variable, and `service set env` makes it
survive later restarts.

10.5 Security note
- `opencode-v2 service get` prints service environment values in plain text.
  It exposed the token once in this session's tool output. The token is not in
  the repository, opencode.jsonc, this report or any project file, but it
  should be treated as exposed to the session log and the model provider.
- Recommended rotation if that log is shared: `gh auth logout --hostname
  github.com`, repeat the device login, then repeat the setenv and
  `service set env` steps.
- The token has repo scope and can read and write the user's repositories.
  Treat it as a credential, not a public identifier.

13.3 Implementation — left constellation (React Three Fiber)

  (radians per second), not frame-count based.

  colours, lights and labels are untouched.

  scaling the stored per-move values by 60 fps and decaying exponentially

  zero immediately and resets the idle timer.

  does not snap or reset.

  user's current angle. Selecting nodes and switching categories are also

13.5 Implementation — right technology panel (CSS 3D)

  existing parallax layer and the existing manual-orbit layer. It applies a
  very slow sway of about +/-2.4 deg yaw and +/-0.4 deg pitch over 46 s with
  a negative animation delay so the scene starts mid-phase.
- Because it is a separate ancestor transform, it composes with the
  existing pointer parallax and manual --wx/--wy orbit values instead of
  modifying them. Object layout, depth, selection and drag rotations are
  unchanged.
- The sway is paused with animation-play-state on pointer down, object drag,
  keyboard rotation, reset, while the panel is off screen, and while the tab
  is hidden. Pausing freezes the phase, so the motion resumes from exactly
  where it stopped. It restarts 2.4 s after the last interaction.

14.1 Why section 13 was not good enough
Section 13 shipped a continuous, unbounded 360-degree yaw. A follow-up
check forced the scene through fixed angles and found a real defect: the
constellation is a nearly flat ring (all NODE_POSITIONS sit at z between
-0.35 and +0.35), so a yaw of about 90 degrees turns it edge-on. The nodes
collapse into a vertical line, the labels collide and the composition is
unreadable. Evidence: audit-yaw-090.png (about 85 degrees), with
audit-yaw-125.png and audit-yaw-170.png showing the ring recovering.
At 61 degrees the "UI - INTERFACE" label already touches the core
(audit-arc-p052.png); at 40-46 degrees the ring is still clean
(audit-arc-m040.png, audit-arc-p036.png). A continuous 360-degree pass
would hit the broken state every quarter turn, so it was replaced.

14.2 Final motion
- The autonomous component is a bounded sine arc added to the user's
  horizontal angle: autoYaw = sin(phase) * 0.32 rad (about +/-18.3 deg).
- Peak arc speed stays the tuned value: 0.030 rad/s on the full tier and
  0.024 rad/s on the lite tier. Mean absolute speed over a cycle is
  0.019 rad/s (1.09 deg/s) and 0.015 rad/s (0.88 deg/s) respectively.
- Period is 67.0 s on full (33.5 s each way) and 83.8 s on lite. The scene
  eases to a stop at each end and reverses, so there is never a jump.
- Everything else from section 13 is unchanged: the same useFrame loop,
  the 2.4 s idle delay, 0.95 s ease-in and 0.18 s ease-out, the manual
  angle preserved on release, the 50 ms delta clamp, reduced-motion
  handling, tab-visibility handling and the right-panel CSS sway.
- The manual yaw range is untouched. If a user deliberately parks the ring
  near the edge-on band, it stays their choice exactly as before; the
  autonomous arc no longer sweeps through that band on its own.
